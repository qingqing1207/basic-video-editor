# 移动后原子清理源空轨道

日期：2026-10-05。状态：实现及自动化通过，浏览器结果见下方最终验收段。

## 最终规则

用户最终确认的是“保持当前拖拽规则，移动后检查参与移动的源轨道是否为空”，不是整轨交换。

1. 保留现有片段拖动、上／下插入线、吸附、横向时间计算、占用检测及新建轨道逻辑。
2. 根据本次实际移动列表收集全部源轨道 ID，单选、多选、联动模式共用同一判断。
3. 在最终移动结果中，源轨道没有任何片段就移除；仍有片段，或同时接收其他移动片段，就保留。
4. 不要求源轨道移动前只有一个片段。同轨多片段全部移走也会清理。
5. 原本为空且未参与本次移动的轨道保留，不做全局空轨清扫。
6. 同轨横向移动不造成源轨变空。取消拖动或移动验证失败，不删除轨道。
7. 如果移空的是主视频轨，提升本次主轨片段实际到达的存续视频轨，保持其显示位置和片段时间；不补建空主轨。
8. 源轨道删除是实际结构删除，目标是已有轨时总轨数可减少；目标是新轨时，新建数量与删除数量分别由原组移动计划和空源轨数量决定。它不意味着两个轨道对象或片段自动交换。

清理只作用于传入本次移动命令的片段，不额外推断／创造音视频链接关系，也不扩大联动选中范围。

特别注意：原版 resolveNewTrackMove 按选中片段分别创建目标轨道，同轨两个片段拖到新轨位置时会产生两条有内容的新轨。此次保留该算法，清理一条源轨后总数仍可能增加一条；这不属于空轨泄漏，也不声称实现了“多片段始终保持同轨”。这项行为已通过源码和本轮 UI 确认。

## 原版与此次问题的来源

原版 `opencut/apps/web/src/core/index.ts` 在每条命令之后的 reactor 中清理全部空 overlay/audio（不清理 main）。原版 `MoveElementCommand` 先提交移动结果，后续 reactor 再提交清理结果。

新增手动轨道管理时，我们移除了这个全局 reactor，目的是让用户主动创建的空轨能够留存。然而片段控制器仍沿用占用位置新建轨道的规则，结果源空轨不断积累。这是我们改变空轨保留策略后引入的回归，不是原版从来没有清理逻辑。

此次只在移动命令里清理本次源空轨，兼顾两种需求。不恢复全局清理，也不以 UI 隐藏空轨代替真实数据处理。

## 原子提交及撤销

`MoveElementCommand.execute()` 先在局部变量中完成：创建目标轨道 → 移动所有片段 → 找出空源轨 → 更新主轨身份和 order/overlay/audio → 一次 `updateTracks(finalTracks)`。

订阅者、渲染和自动保存不会接收到“先多出一个轨道，再删除源轨”的中间结构。不使用 useEffect、延迟清理、第二条删除命令或删除动画。用户仍会看到正常拖动预览和最终落点后的行位置变化，不承诺轨道总数减少时页面高度不变。

命令保存移动前的完整轨道快照，选择结果使用目标轨道 ID。一次撤销恢复片段、源轨道、原始顺序和选择；一次重做重新完成移动和清理。跨轨落下之前将仍处于时间线内的焦点移交给编辑器根节点，避免被删除的片段 DOM 将焦点丢到 body，允许松手后直接撤销；不抢宿主输入焦点。

没有新增轨道拖动手柄、禁止重叠的新规则或拖拽库。前期为已放弃方案安装的 dnd-kit 已从依赖及锁文件移除。

## 自动化验收

新增 9 项测试，全套目前 117 项通过。覆盖：

- 新轨插入与源轨清理只向订阅端发布一次结果；一次撤销／重做恢复轨道、内容、时间及选择。
- 移入已有空位，保留未参与移动的手建空轨。
- 源轨仍有片段、同轨水平移动不清理。
- 实际 group planner 生成同轨多片段＋音频跨轨计划，在 ripple 关闭及开启两种情况下清理源轨，保留相对时间；只发布一次。
- 同一次操作中源轨接收其他片段，按最终非空状态保留。
- 主轨转移到新目标轨，保持目标显示位置与非零开始时间，撤销／重做身份正确。
- 连续 20 次往返移动不累计源空轨。
- 类型验证失败不发布任何中间轨道，也不进入历史。
